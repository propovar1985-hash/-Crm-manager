# Безопасные изменения CRM

## Обязательный порядок
1. Создавать отдельную ветку от актуального `main`.
2. Вносить изменение только в нужные файлы; не заменять весь проект старой копией.
3. Перед коммитом проверить JavaScript: `node --check имя-файла.js`.
4. Открыть Pull Request в `main`.
5. Дождаться обязательной проверки **Validate CRM before release**.
6. Если проверка не прошла — исправить ошибки и повторить проверки. Не сливать PR с красной проверкой.
7. После слияния проверить публикацию GitHub Pages и доступность обновлённых файлов.

## Правила разработки
- Не менять Supabase URL, ключи, схему БД и авторизацию без отдельной задачи и плана миграции.
- Не удалять существующие функции и разделы при локальной доработке.
- Перед изменением читать актуальную версию файла из репозитория.
- Для новых JS-файлов добавлять проверки критичных функций в `scripts/validate-crm.mjs`.
- Для изменения поведения добавлять тест, который обнаруживает именно прежнюю ошибку.
- Увеличивать cache-buster подключаемого файла в `index.html`, если это необходимо для обновления браузерного кеша.
- Считать задачу выполненной только после успешной проверки и успешной публикации.

## Что проверяется автоматически
- синтаксис всех JavaScript-файлов;
- наличие локальных скриптов, подключённых в `index.html`;
- критичные параметры 3D-конструктора;
- ряд ключевых функций сметы и печати.

Проверки не заменяют ручной тест интерфейса, расчётов, Supabase и браузерной печати.
